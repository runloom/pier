# 周期审查的接入范围

状态：用户已确认先接入官方定时能力、继续修复状态，并独立规划 Pier 入口。本文件是接入方案；**平台任务尚未启用，Pier 调度功能尚未实现**。

## 本次落地顺序

1. 修复 [源码审查](../specs/2026-09-06-agent-status-industry-audit.md) 的 F1–F5；状态准确性不依赖定时任务。
2. 用 Codex 官方应用定期执行研究任务，沿用 [完整任务提示词](agent-status-periodic-review.md)。每周一 10:00，Asia/Shanghai；只审查和写报告，产品修复单独实施。
3. 先验证周期审查能持续带来有效建议，再决定是否建设跨智能体的 Pier 管理入口。

## 已验证的接入条件与障碍

| 项目 | 2026-09-06 核验结果 |
|---|---|
| 官方产品 | [Automations 文档](https://learn.chatgpt.com/docs/automations?surface=app) 提供定时管理；CLI/IDE 可准备提示词，管理入口在支持的网页或桌面应用 |
| 本地项目 | 官方桌面任务需要电脑开机、应用运行；仅把本机路径填进云端任务不能访问未提交的工作区 |
| 当前会话工具 | 没有创建/更新定时任务的可调用工具 |
| 应用控制 | 初始化失败：`failed to write kernel assets: No such file or directory`，未进入任务创建界面 |
| 备用应用控制 | 独立 Computer Use 的应用查询未返回结果，已停止等待；未进入创建或确认步骤 |
| 本机公开协议 | Codex 0.153.4 的 `app-server generate-ts --experimental` 中，`ClientRequest` 无 scheduled-task/automation CRUD；`ScheduledTaskSummary` 仅见于 `PluginDetail.scheduledTasks` 元数据，不能据此执行创建 |
| Pier 现状 | `packages/plugin-codex/src` 与 `packages/plugin-tasks/src` 没有周期创建入口；后者对接外部任务来源，不是时钟调度器 |

因此本轮不能取得平台任务 ID、启用状态和下一次执行时间，不能声称“已设置成功”。不直接写官方应用的私有数据库，也不以系统 cron 替代用户确认的官方任务。

管理入口恢复后，最后一步是按模板创建任务并读回：任务 ID、启用状态、时区、周期、项目目录、提示词与下一次执行时间。用户已授权本配置，无须再次询问相同权限。首次自动运行后还需确认实际写出了有本地源码证据的报告；报告内容基线不能代替定时执行验收。

## Pier 是否需要提供支持

单个 Codex 周期审查先复用官方应用。Pier 管理入口的价值只有在用户需要跨 Codex、Claude、Kimi，统一选择项目、查看执行结果并回到对应面板时才成立。

未来优先使用提供方公开的管理能力：官方平台负责时间触发和执行，Pier 负责自身项目、窗口、面板和通知导航。能力必须逐提供方验证，不承诺所有智能体都拥有相同的定时 API；不得因为某处出现 `ScheduledTaskSummary` 类型就展示虚假的创建按钮。

如果需求进一步要求“Pier 自己按时启动任意 CLI”，这将实质引入自动调度，与 [PRODUCT.md](../../../PRODUCT.md) 和 [AGENTS.md](../../../AGENTS.md) 当前边界不同，应作为独立产品变更设计。不能借状态修复悄悄加入宿主调度器。

该独立变更至少要明确：

- 谁负责唤醒和触发；退出 Pier、电脑睡眠、断网或错过时间后如何处理。
- 时区和夏令时；同一任务前次未完成时是否跳过本次，如何防止重复执行。
- 项目访问范围、工作目录、执行权限、预算与最长执行时间。
- 复用原生 CLI 的执行和取消方式，不自造模型请求协议；成功、失败、取消和等待必须有真实结果。
- 用户能查看最近结果、暂停与恢复；系统结果复用消息中心，不能把“已启动”写成“已完成”。

在这些边界明确前，当前交付保持为“状态修复 + 可配置的官方周期审查 + 独立入口规划”。
